## 1. 가장 큰 교훈 — 측정 전 판단은 틀렸다

### 무슨 일이 있었나
파일 목록과 README만 보고 초기 검토에서 이렇게 결론지었다.

> "zip A(47청크)는 v1이고 zip B(v2.3, 135청크)가 성숙한 상위 호환이다.
> v2.3이 원본 2종도 품고 있으므로 **v1은 사실상 대체됐다**."

그럴듯했다. 135 > 47이고, v2.3에는 위키 문서 22종·임베딩 가이드·벡터 DB 업로드
스크립트 6종까지 있었다. 구조도 더 정교해 보였다.

**감사 하네스를 돌리자마자 뒤집혔다.**

| | v1 | v2.3 |
|---|---|---|
| 청크 수 | 47 | 135 |
| 중앙값 토큰 | 658 | **298** |
| retrieval_questions | 3.4개/청크 | **0개** |
| priority/confidence/freshness | 전건 보유 | **전건 부재** |
| 어휘 중복(Jaccard≥0.3) | — | 47개 중 **2개만** 겹침 |
| 주제 중복 | — | 47개 중 **32개는 주제 자체가 v2.3에 없음** |

v1과 v2.3은 대체 관계가 아니라 **상보 관계**였다. v1을 버렸다면 32개 주제와
메타데이터 설계 전체를 잃었을 것이다.

### 왜 틀렸나
- **양을 품질로 착각했다.** 135개가 47개보다 낫다는 무의식적 가정.
- **README를 검증으로 착각했다.** v2.3 README는 구조를 훌륭하게 설명한다. 하지만
  README는 저자의 의도이지 산출물의 실측이 아니다.
- **구조의 정교함을 내용의 정교함으로 착각했다.** 7섹션 고정 템플릿은 정교해 보이지만
  바로 그것이 과분할과 빈 청크의 원인이었다.

### 규칙으로 만든다
> **파일을 세지 말고 내용을 재라. 판단 전에 하네스를 먼저 쓴다.**
> 감사 스크립트 작성에 든 시간은 잘못된 병합을 되돌리는 비용보다 항상 싸다.

## 2. 내가 만든 버그 — 조용한 데이터 유실

### 코드
```python
# 마지막 조각이 너무 작으면 직전 버킷과 합친다
if len(buckets) > 1 and sum(s["tokens"] for s in buckets[-1]) < TARGET_LO // 2:
    buckets[-2] += buckets.pop()          # ← 결함
```

### 무슨 일이 벌어지나
`a[-2] += b`는 다음 순서로 실행된다.
1. `buckets[-2]` 로드 → 당시 리스트 길이 3 기준으로 **1번 원소**
2. `buckets.pop()` 평가 → 리스트가 **길이 2로 줄어듦**
3. `__iadd__`로 1번 원소를 제자리 변경
4. 결과를 `buckets[-2]`에 저장 → 이제 `-2`는 **0번 원소**

즉 1번 원소를 고쳐 놓고 0번 자리에 써 넣는다. 실측 결과:

```
병합 전: [[073, 074], [075], [076, 077]]
병합 후: [[075, 076, 077], [075, 076, 077]]    ← 073, 074 소멸
```

`chunk.073`(정의)과 `chunk.074`가 **통째로 사라졌고**, 동일 내용 청크가 2개 생겼다.

### 어떻게 잡았나
직접 눈으로 본 게 아니다. T-06 중복 시험이 **Jaccard 0.986** 쌍을 뱉었고,
"내가 만든 청크끼리 왜 98% 같지?"라는 의문에서 diff → bucket 계산 재현 순으로 추적했다.

**시험이 없었다면 조용히 넘어갔을 것이다.** 출력 청크 수는 정상으로 보였고,
로그에도 오류가 없었으며, 유실된 것은 "원래 없던 것"과 구분되지 않는다.

### 교훈 3가지
1. **음수 인덱스 + 제자리 변경 + 컨테이너 크기 변화**를 한 문장에 섞지 않는다.
   `pop()` 결과를 변수에 받고 양수 인덱스로 쓴다.
2. **변환 파이프라인에는 보존 불변식을 심는다.** 입력 조각이 출력에 정확히 1회씩
   등장하는지 `assert`로 확인한다. 지금은 빌더가 이걸 강제한다(T-10).
   ```python
   flat = [s["cid"] for b in buckets for s in b]
   assert sorted(flat) == sorted(s["cid"] for s in keep)
   ```
3. **중복 검사는 품질 지표가 아니라 버그 탐지기다.** T-06을 "청크 품질 항목"으로
   넣었는데 실제로는 내 코드 버그를 잡았다.

## 3. 수정이 다음 결함을 낳았다

버그를 고친 뒤 빈 청크(`해당 없음`)를 제거했더니, 그 조각에 의존하던 앞쪽 버킷이
128토큰으로 홀로 남았다. 꼬리 하나만 병합하던 로직으로는 중간에 생긴 소형 버킷을 못 잡았다.

**교훈**: 특수 케이스(꼬리)만 처리하는 로직은 입력이 바뀌면 반드시 새는 곳이 생긴다.
"모든 소형 버킷을 인접에 흡수"라는 **일반 규칙**으로 다시 썼고, 그러자 이 부류의 문제가 끝났다.

수정 3회의 흔적:

| 회차 | 조치 | T-01 범위 내 | 부작용 |
|---|---|---|---|
| 1차 | 섹션 병합 도입 | 8.9% → 56.4% | aliasing 버그로 2청크 유실 |
| 2차 | aliasing 수정 + 빈 청크 제거 | 56.4% | 128토큰 고아 버킷 발생 |
| 3차 | 소형 버킷 일반 흡수 | 55.0% (청크 수 정상화) | 없음 |

## 4. 자동 생성물에 정직한 라벨을 붙였다

v2.3 유래 46개 청크의 `retrieval_questions`는 섹션 종류별 템플릿으로 기계 생성했다.

```python
"operations": ["{t} 운영 시 주의점은?", "{t}의 모범 사례는?"]
```

이건 사람이 쓴 v1의 질문과 품질이 같지 않다. 그래서 **섞어 놓고 같은 것처럼 취급하지 않았다.**

- 청크에 `confidence: auto-merged` 표시
- 골든셋 생성기가 `question_origin` 필드를 남겨 **출처별 집계**를 강제
- `ingestion.yaml`에 `confidence: ["verified"]`만 남기는 strict 필터 경로 마련

**교훈**: 자동 생성물을 사람 산출물과 구분 없이 섞으면, 나중에 품질 문제가 생겼을 때
어디부터 봐야 할지 알 수 없게 된다. **생성 시점에 라벨을 붙이는 비용이 가장 싸다.**

같은 이유로 신규 집필 7종은 전부 `confidence: draft`이고, 본문에 "집필 근거" 블록을 넣어
원본에 근거가 있는 부분과 내 설계 판단을 구분했다.

## 5. 골든셋이 공짜로 나왔다 — 그리고 그게 함정이다

각 청크의 `retrieval_questions`가 곧 (질의, 정답) 쌍이므로 100청크에서 **408쌍**이
라벨링 없이 나왔다. 검색 회귀셋을 즉시 확보한 셈이다.

**그리고 실제로 돌려보니 예상보다 훨씬 나빴다.**

| 색인 대상 | Recall@1 | Recall@10 |
|---|---|---|
| 제목+태그+질문+본문 | 0.983 | **1.000** |
| 본문만 | 0.505 | 0.944 |

Recall@10 = 1.000은 성능이 아니라 **누출**이다. 질문을 임베딩 텍스트에 넣어 두고
그 질문으로 검색했으니, 정답을 색인해 놓고 찾은 것이다. "낙관적"이라고 미리 적어
두었지만 실제로는 **측정 불가 수준**이었다. 경고를 적어두는 것과 그 크기를 아는 것은
다른 일이다.

**교훈 둘**:
1. 질의 생성에 쓴 필드는 **평가용 색인에서 제외**한다. 이제 `--mode body`가 유일하게
   유효한 수치다.
2. 공짜로 얻은 평가 데이터는 대개 공짜인 이유가 있다. 편향의 **방향만 적지 말고
   크기를 재라.**

## 6. 도구가 없을 때 정직하게 대체하기

`tiktoken` 설치는 됐지만 BPE 파일 다운로드가 프록시에 403으로 막혔다.

```
ProxyError: openaipublic.blob.core.windows.net — Tunnel connection failed: 403
```

선택지는 셋이었다.
1. 토큰 시험을 포기한다
2. 대충 문자 수로 세고 "토큰"이라 부른다
3. 추정식을 명시하고 한계를 함께 보고한다

3번을 택했다. 문자 클래스별 가중합을 쓰되 **`TEST-PLAN.md`에 가중치 근거와 ±20% 밴드를
적었고, "절대값을 신뢰하지 말 것, 상대 비교에만 쓸 것"을 명시**했다.

**교훈**: 측정 도구가 없다고 측정을 건너뛰면 판단 근거가 사라진다. 대체 수단을 쓰되
**한계를 산출물에 박아 넣는다.** 나중에 이 숫자를 보는 사람이 오해하지 않도록.

## 7. 원본에서 배운 것 — 템플릿의 양날

v2.3의 7섹션 고정 템플릿(definition/setup/operations/exceptions/security/related/sources)은
**커버리지를 보장했지만 빈 칸도 함께 생산했다.**

```
# 트러블슈팅 가이드 - 설정법
해당 없음 — 트러블슈팅 가이드는 문제 발생 시 참조용입니다.
```

그리고 크기를 전혀 통제하지 못했다. 같은 문서의 조각들이 95 / 59 / **1623** / 155 / 136 토큰.

**교훈**:
- 고정 템플릿은 "빠뜨림 방지"에는 좋고 "적정 크기"에는 무력하다. 두 목적을 한 장치로 풀지 않는다.
- 템플릿이 강제한 빈 섹션은 **채우지 말고 지운다.** "해당 없음"은 검색 오염이다.
- 의미 단위 분할과 크기 제어는 별개 단계로 둔다 — v3.0은 섹션으로 나누고 크기로 다시 합친다.

현재 100청크 전부 빈 값이다.

**지금 넣는 비용은 0이고, 나중에 넣으면 100청크 재빌드 + 재임베딩이다.** 스키마 필드

그래서 4종 결함을 일부러 담은 픽스처를 만들고, **감사가 FAIL을 내는지**를 게이트에서

```
run "T-13 자기시험" bash -c '! python3 tools/kb_audit.py tests/fixtures/t13_broken/chunks ...'
```

## 10. 어댑터를 쓰고 나서 안 것 — DB마다 메타데이터 제약이 다르다

v2.3 업로드 스크립트를 그대로 못 쓴 이유는 파일 형식(JSON 배열 vs JSONL)이 다르기
때문이라고 생각했다. 그건 부차적이었다.

**진짜 이유는 벡터 DB마다 메타데이터 타입 제약이 다르다는 것이다.**

| 타깃 | 리스트 | 중첩 객체 |
|---|---|---|
| ChromaDB | ✗ | ✗ |
| Pinecone / Weaviate | ✅ | ✗ |
| Qdrant / FAISS | ✅ | ✅ |

ChromaDB는 `tags: ["a","b"]`를 받지 못한다. 평탄화 없이 넣으면 적재가 실패하거나,
더 나쁘게는 메타데이터 필터가 조용히 동작하지 않는다. `audience` 필터로 역할별 뷰를
만들려던 설계가 통째로 무력해진다.

**교훈**: 어댑터는 "형식 변환"이 아니라 **"제약 흡수"**다. 대상별 제약표를 코드에
명시적으로 두고, 적재 전에 검증한다(`--dry-run`). 이 검증은 외부 패키지 없이 돌아야
CI에서 매번 확인된다.

## 11. 다음 사람을 위한 체크리스트

지식 베이스를 통합·이관할 때:

- [ ] **판단 전에 측정한다.** 파일 수·README·디렉터리 구조는 품질 신호가 아니다
- [ ] 두 세트를 합치기 전 **어휘 중복과 주제 중복을 따로 잰다** (둘은 다른 값이다)
- [ ] 변환 파이프라인에 **보존 불변식 assert**를 넣는다
- [ ] 중복 검사를 돌린다 — 품질 지표가 아니라 **버그 탐지기**로
- [ ] 자동 생성물에 **생성 시점에** 라벨을 붙인다
- [ ] 파생물과 원본을 **같은 인덱스에 넣지 않는다** (ingestion include/exclude 명시)
- [ ] 절대경로 하드코딩을 찾는다 — 남의 스크립트에 흔하다
- [ ] 측정 도구가 없으면 **대체 수단의 한계를 산출물에 적는다**
- [ ] 통과하지 못한 시험을 **통과한 것처럼 요약하지 않는다**
- [ ] **한 번도 발화하지 않은 검사는 픽스처로 작동을 증명한다**
- [ ] 나중에 쓸 스키마 슬롯은 **지금 열어둔다** (필드 추가 = 재빌드 + 재임베딩)
- [ ] 벡터 DB **메타데이터 타입 제약**을 어댑터가 흡수하게 한다

## 12. 이번 작업이 하지 못한 것

기록해 둔다. 이 목록이 다음 작업의 시작점이다.

- **내용 사실성을 검증하지 않았다.** 청크의 인용 수치·버전·URL은 구조 시험을 통과했을 뿐
  사실 대조를 거치지 않았다. (2026-08-08 갱신: MCP 2026-07-28 항목은 §13.5로 해소했다.) 프롬프트 D(개별 청크 심층 검토)는 외부 공식 문서 접근이
  프록시에 막혀 수행 불가였고, **근거 없이 통과 판정을 내리는 대신 미실행으로 남겼다.**
- **dense 검색 성능을 측정하지 않았다.** 어휘 검색 하한만 냈다.
  어댑터는 준비했고 dry-run은 통과하지만 **실적재는 실행하지 못했다**(클라이언트 패키지 부재).
  (2026-08-08 갱신: `--dense-runs`로 외부 순위 파일을 받는 경로를 열었으나 여전히 미실행이다.
  held-out 실측으로 어휘 검색 상한이 Recall@10 0.475임을 알게 됐다 — 나머지는 dense에 있다.)
- **임베딩 모델을 비교하지 않았다.** `bge-m3` 권장은 코퍼스 성격(한국어+영어 혼용)과
  폐쇄망 제약에서 도출한 **설계 판단이지 측정 결과가 아니다.**
- **원본의 커뮤니티 블로그 의존을 해소하지 못했다.** 원본 스스로 경고하듯 hook 이벤트 개수
  (27/30/12로 출처마다 다름), 기업 도입 수치(Coinbase 5%, Ramp 50% 등)는 2차 인용이다.
  사내 규칙으로 승격시킬 항목은 공식 문서 재확인이 선행되어야 한다.

**현재 상태를 한 문장으로**: 구조는 검증됐고 내용은 검증되지 않았다.

> 2026-08-08 갱신: 여기에 한 줄을 더 붙여야 했다 — **검색도 검증되지 않았다.**
> 두 번째 반복에서 어휘 검색은 전면 측정하고 게이트에 연결했다(§13).
> dense는 여전히 미측정이고, held-out 40건은 실제 사용자 로그가 아니라 AI가 지어낸 것이다.

## 13. 두 번째 반복에서 배운 것 (2026-08-08)

### 13.1 "측정만 하고 막지 않는 검사"는 검사가 아니다

`ci/gate.sh`는 검색 평가를 돌리고 있었다. 다만 `|| true`가 붙어 있었다.
수치는 `out/retrieval.json`에 잘 남았고 아무도 보지 않았으며, Recall이 절반으로
떨어져도 CI는 초록이었다.

**§1의 교훈("판단 전에 측정하라")에는 뒷면이 있다 — 측정한 것을 판정에 연결하지 않으면
측정하지 않은 것과 같다.** 구조 검사(T-03~T-08)는 처음부터 차단이었는데
검색만 아니었던 이유는 단순하다. 기준선이 없어서 무엇을 기준으로 막을지 몰랐기 때문이다.
기준선을 만들자 문제가 사라졌다.

### 13.2 편향의 크기를 재고 나서야 방향을 알았다

§5는 골든셋 누출을 발견하고 "본문 전용이 유일하게 유효한 수치"라고 결론지었다.
그 결론은 맞았지만 **거기서 멈춘 것이 문제였다.** 본문 전용 0.944도 실제 질의
성능이 아니었다.

held-out 세트를 만들자 같은 색인에서 Recall@10이 **0.267**로 나왔다.
격차 0.68은 시험 계획이 예상한 "낙관 편향" 수준이 아니다.

단서는 이미 있었다. 출처별 분해에서 **사람이 쓴 `authored` 질문이 늘 가장 낮았다.**
그 신호를 "표본이 적어서"로 넘겼는데, 실제로는 "질문이 사람 어휘에 가까울수록 점수가
떨어진다"는 곡선의 한 점이었다.

**규칙**: 편향을 발견하면 방향만 적지 말고 **끝까지 재라.** 편향이 있는 세트를 고쳐
쓰는 것과, 편향 없는 세트를 새로 만드는 것은 다른 일이다.

### 13.3 하지 않기로 한 변경을 근거와 함께 기록한다

이번에 계획했던 변경 두 건을 **재빌드 전에 상한을 재 보고 취소했다.**

- FAQ 어트랙터 분할 — 오라클로 완벽히 제거해도 프로덕션 설정에서 nDCG +0.0037
- Contextual Retrieval 헤더 — 평균 nDCG +0.015이지만 질의 단위로 11건 개선 / 8건 악화

둘 다 실행했다면 101청크 재빌드·재임베딩·기준선 재설정이 따라왔다. FAQ 분할이
조치 목록에 있었던 이유는 **본문 전용 수치만 보고 판단했기 때문이다** — 그 색인에서는
이득이 +0.028로 8배 커 보였다.

**규칙**: 변경 비용이 큰 작업은 **오라클 상한을 먼저 재라.** "완벽하게 해냈을 때
얼마나 좋아지는가"는 대개 실제 구현보다 싸게 계산할 수 있고, 그 값이 작으면
구현은 볼 것도 없다.

그리고 **하지 않기로 한 결정도 산출물이다.** 근거 없이 목록에서 지우면 다음 사람이
같은 항목을 다시 제안한다.

### 13.4 작동하지 않는 통제를 설정 파일에 적지 않는다

범위 밖 질의를 거르는 점수 하한을 넣으려 했는데, 분리도 AUC가 0.5913이었다 —
범위 밖 질의의 1위 점수 중앙값이 **범위 안보다 높았다.** 어떤 하한도 작동하지 않는다.

임의의 값을 하나 골라 `score_floor: 12`라고 적을 수도 있었다. 그러면 다음 사람은
기권 통제가 있다고 믿는다. `score_floor: null`과 AUC를 함께 적었다.

**규칙**: 설정 파일의 값은 **작동한다는 주장**이다. 측정하지 않았거나 측정 결과
작동하지 않으면 그렇게 적는다. `ingestion.yaml`의 `retrieval` 절이 hybrid·rerank·
2홉 확장을 구현도 수치도 없이 선언하고 있었던 것도 같은 문제였다 —
이제 각 항목이 `measured` 플래그를 갖는다.

### 13.5 접근이 막혔다고 결론 내리기 전에 다른 경로를 본다

U-001은 "modelcontextprotocol.io가 HTTP 403"이라 미확인으로 남아 있었다.
사실 사양의 **원문 마크다운은 raw.githubusercontent.com으로 그대로 열린다.**
렌더링된 사이트가 필요했던 적이 없었다.

그 경로로 2026-07-28 changelog를 읽자, 기존 서술은 전부 맞았지만 KB에 한 건도 없는
항목이 열 개 넘게 나왔다(`server/discover`, `subscriptions/listen`, MRTR 필드명,
`ping` 제거 등). **"확인 못 함"이 "확인했더니 불완전함"으로 바뀌는 데 필요한 것은
다른 URL 하나였다.**
