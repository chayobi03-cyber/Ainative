# RAG 제작 에이전트 설계 기록

이 문서는 v3.0 제작 과정에서 **재사용 가능하다고 판명된 절차**를 에이전트 명세로 정리한 것이다.
목적은 "다음 지식 베이스를 만들 때 이 과정을 자동화할 수 있게" 하는 것이다.

---

## 0. 결론부터 — 무엇을 만들고 무엇을 가져다 쓸 것인가

**대부분은 만들지 마라.** 이 작업에서 실제로 고유했던 부분은 좁다.

| 기능 | 권장 | 이유 |
|---|---|---|
| 문서 파싱·변환 | **기존 도구** (`docling`, `unstructured`) | PDF/Office 파싱은 이미 해결된 문제 |
| 의미 기반 청킹 | **기존 도구** (`chonkie`, `semchunk`) | 신규 문서 청킹은 라이브러리가 낫다 |
| RAG 품질 평가 | **기존 도구** (`ragas`, `deepeval`) | faithfulness·context precision 등 dense 지표는 직접 만들 이유 없음 |
| 프롬프트/검색 회귀 | **기존 도구** (`promptfoo`) | 회귀 게이트 CI 통합이 이미 됨 |
| 관측 | **기존 도구** (Langfuse — 이 KB가 이미 권장) | 폐쇄망 셀프호스팅 가능 |
| 에이전트 패키징 | **Claude Code Skill + plugin** | 별도 프레임워크 불필요. 이 KB가 그 방법을 문서화하고 있다 |
| **구조 감사 하네스** | **직접 유지** (`tools/kb_audit.py`) | 아래 §1 참조 — 기성품에 없다 |
| **정정 원장** | **직접 유지** (`kb/corrections.yaml`) | 아래 §2 참조 — 기성품에 없다 |
| **confidence 분류** | **직접 유지** | 아래 §3 참조 |

즉 **새 에이전트 프레임워크를 만들 필요는 없다.** 이 저장소의 3가지 고유 자산을
Claude Code Skill로 감싸고, 나머지는 기존 라이브러리를 호출하면 된다.

## 1. 고유 자산 ① 구조 감사 하네스

기성 RAG 평가 도구(`ragas` 등)는 **검색·생성 품질**을 본다. 청크 세트 자체의 구조적
무결성은 보지 않는다. 이번에 실제로 잡아낸 것들이 그 영역이다.

| 잡아낸 것 | 기성 도구가 잡는가 |
|---|---|
| `retrieval_questions` 전건 부재 (135청크) | ✗ |
| 중앙값 298토큰 과분할 | ✗ |
| 내용 없는 채움 청크 (`해당 없음`) | ✗ |
| 깨진 `related_chunks` 참조 | ✗ |
| **병합 버그로 인한 청크 유실** | ✗ |
| 코드 펜스 짝 불일치 | ✗ |

특히 마지막 두 개가 중요하다. **중복 검사(T-06)는 품질 지표가 아니라 버그 탐지기로
작동했다** — Jaccard 0.986 쌍이 내 병합 로직의 aliasing 버그를 드러냈다.

### 에이전트에 넣을 규칙
```
변환 파이프라인을 만들 때는 반드시 보존 불변식을 심는다.
  입력 조각 ID 집합 == 출력 조각 ID 집합
이 assert 없이 변환을 돌리면 유실이 조용히 지나간다.
```

## 2. 고유 자산 ② 정정 원장 (`corrections.yaml`)

**해결한 문제**: 생성 청크를 직접 고치면 다음 빌드에서 되돌아간다. 그런데 원본이
손에 없으면(외부 Drive, 타 팀 산출물) 고칠 경로 자체가 없다.

**설계**:
```yaml
corrections:
  - id: C-001
    verified_source: <1차 출처 URL>      # 필수. 2차 인용으로 고치지 않는다
    replace: [{from: ..., to: ...}]
    set_meta: {freshness: ...}
verified_no_change: [...]                 # 확인했는데 맞았던 것도 남긴다
unverified: [...]                         # 확인 못 한 것도 남긴다
```

**핵심 규칙 3가지**
1. `applies: 0`이면 **빌드 실패**. 이미 반영된 정정이 남아 있으면 원장이 썩는다.
2. "확인했는데 맞았다"와 "확인 안 했다"는 **다른 상태**다. 둘 다 기록한다.
3. 정정은 1차 출처를 동반한다.

실제 효과: MCP 2026-07-28이 RC → stable로 바뀐 것을 3개 청크에 일괄 반영했고,
누가 언제 무슨 근거로 고쳤는지가 남았다.

## 3. 고유 자산 ③ confidence 분류

자동 생성물과 사람 산출물을 **생성 시점에** 구분한다. 나중에 하려면 못 한다.

| 값 | 의미 | 프로덕션 검색 |
|---|---|---|
| `verified` | 사람 작성·검증 | 포함 |
| `mixed` | 검증 내용 + 벤더 주장 혼재 | 제외 |
| `auto-merged` | 자동 병합·자동 생성 질문 | 포함 |
| `draft` | 신규 집필, 사내 실정 미반영 | 제외 |

**정본은 `kb/ingestion.yaml`의 `retrieval.filters`다.** 이 표는 그 값을 옮겨 적은 것이고,
`tools/check_consistency.py --only policy`가 둘이 어긋나면 CI를 막는다.
같은 정책이 세 문서에 적혀 있었고 서로 달랐던 적이 있다 — 이 표는 `mixed`와 `draft`를
프로덕션에 포함한다고 적었지만 실제 설정은 제외하고 있었다.

경계가 왜 여기인가: `mixed`는 검증되지 않은 벤더 주장이 섞여 있어 사실 오답이 될 수
있고, `draft`는 사내 실정이 비어 있어 그럴듯한 오답이 된다. 반면 `auto-merged`는
본문 자체는 사람이 쓴 것이고 자동 생성된 것은 질문뿐이라 프로덕션에 넣는다.
사실 확인이 필요한 질의에서는 `strict` 경로로 `verified`만 남긴다.

## 4. 에이전트 워크플로우 (검증된 순서)

```
[1] 내용 선별 (싸게, 표본)
     └ 유지 가치 / 주제 커버리지 / 출처가 1차인가 2차인가
[2] 구조 감사 — 판단 전에 측정
     └ 크기 분포, 메타데이터, 참조 무결성, 중복, 카테고리 균형
     └ 두 세트를 합칠 때: 어휘 중복과 주제 중복을 따로 잰다
[3] 변환 (청킹·스키마 통일·병합)
     └ 보존 불변식 assert 필수
[4] 갭 분석 → 신규 집필
     └ 신규분은 confidence: draft
[5] 사실 검증 — 조기 만료 항목 우선
     └ 정정은 원장에 기록
[6] 검색 평가
     └ 골든셋 자동 생성 + held-out 병행
```

### 각 단계의 함정 (실제로 밟은 것)

| 단계 | 함정 |
|---|---|
| [2] | **파일 수·README를 품질 신호로 읽음.** "135 > 47이니 상위 호환"이라 판단했다가 측정에서 뒤집혔다 |
| [3] | 음수 인덱스 + 제자리 변경 + 컨테이너 크기 변화를 한 문장에 섞음 → 데이터 유실 |
| [3] | 꼬리만 처리하는 특수 케이스 로직 → 입력이 바뀌자 중간에 구멍 |
| [6] | **골든셋 순환 참조** — 아래 §5 |

## 5. 가장 값비싼 교훈 — 골든셋 순환 참조

`retrieval_questions`를 임베딩 텍스트에 넣고, **그 질문으로 검색 평가를 했다.**

| 색인 대상 | Recall@1 | Recall@10 | MRR |
|---|---|---|---|
| 제목+태그+질문+본문 | 0.983 | **1.000** | 0.991 |
| 제목+태그+질문만 | 0.983 | **1.000** | 0.991 |
| **본문만** | **0.505** | **0.944** | 0.668 |

앞의 두 줄은 **아무것도 측정하지 않는다.** 정답을 색인에 넣어두고 그걸로 찾은 것이다.
Recall@10 = 1.000은 성능이 아니라 누출이다.

### 에이전트에 넣을 규칙
```
질의 생성에 쓴 필드는 평가용 색인에서 제외한다.
retrieval_questions로 골든셋을 만들었다면, 평가 색인은 본문만으로 구성한다.
그리고 실제 사용자 질의 30건 이상을 held-out으로 반드시 병행한다.
```

## 6. 발견한 검색 설계 이슈 — 다주제 어트랙터

본문 전용 색인에서 오답 1위를 분석한 결과:

| 청크 | 오답 1위 횟수 | 토큰 |
|---|---|---|
| `v3-faq` | **53** | 1,052 |
| `v3-08-context-engineering-01` | 11 | 1,202 |
| `v3-05-claude-md-memory-02` | 10 | 992 |

`v3-faq`는 크기가 크지 않다(1,052토큰, 정상 범위). 문제는 **다주제**라는 것이다.
FAQ는 여러 주제를 얕게 다루므로 많은 질의에 부분 매칭되고, 정작 그 주제를 깊이 다루는
청크의 top-1을 뺏는다. 체크리스트 청크도 같은 성질을 갖는다.

**단, 이 중 상당수는 실제 오답이 아니다.** 예를 들어
"Claude Code에 MCP 서버를 어떻게 등록하는가?"의 정답 라벨은 `v3-cli-registration`이지만
검색 결과 1위인 `v3-03-mcp-setup`도 옳은 답이다. **골든셋의 단일 정답 라벨 편향**이며,
5.6%의 실패율은 실제 오답률을 과대평가한다.

### 완화안 (다음 반복)
1. FAQ·체크리스트를 **질문 단위 청크로 분할**한다
2. 다주제 청크에 검색 시점 페널티를 준다
3. 골든셋을 **복수 정답 허용**으로 바꾼다

## 7. Skill로 패키징하기

새 프레임워크 대신 Claude Code Skill 하나로 감싼다.

```
.claude/skills/rag-kb-build/
├── SKILL.md              # 언제 쓰는가 + §4 워크플로우
├── scripts/
│   ├── kb_audit.py       # 이 저장소에서 그대로
│   ├── build_chunks.py   # 프로젝트별 변환 로직
│   ├── make_golden.py
│   └── eval_retrieval.py
└── references/
    ├── schema.md         # 청크 frontmatter 정본 스키마
    ├── corrections.md    # 정정 원장 규약
    └── pitfalls.md       # §4 함정표 + §5 순환 참조
```

`SKILL.md`의 `description`에 **"언제 쓰는가"를 반드시 넣는다** — 이 KB 자체가
description 품질이 트리거 정확도를 좌우한다고 기록하고 있다.

### SKILL.md description 초안
```
지식 베이스를 RAG용 청크로 만들거나, 기존 청크 세트를 통합·감사할 때 사용한다.
문서 뭉치를 받아 청킹·스키마 통일·품질 감사·골든셋 생성·검색 평가까지 수행한다.
두 개 이상의 청크 세트를 합쳐야 할 때, 청크 품질을 점검해야 할 때,
사실 정정을 추적 가능하게 반영해야 할 때 쓴다.
```

## 8. 이 기록이 다루지 않는 것

- **dense 검색 평가** — 벡터 DB 미적재. `ragas`/`deepeval`을 쓰면 되므로 직접 만들지 않는다
- **문서 파싱** — 이번 입력이 이미 마크다운이었다. PDF/Office는 `docling` 사용 권장
- **증분 인덱싱 구현** — 설계만 `chunks/v3-rag-pipeline-design.md`에 있고 코드는 없다
- **다국어** — 한국어+영어 혼용 단일 축만 다뤘다
