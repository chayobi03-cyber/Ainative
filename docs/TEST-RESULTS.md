### B-1 — 병합 로직의 aliasing 버그로 청크 2개 유실 (심각)

```python
buckets[-2] += buckets.pop()      # 결함
```
`buckets.pop()`이 먼저 평가돼 리스트가 줄어들면서 `-2`가 한 칸 밀린다. 결과적으로
**다른 버킷을 덮어쓰고** `chunk.073`, `chunk.074`를 통째로 유실시켰다.

- 검출: T-06 중복 시험이 Jaccard **0.986** 쌍을 잡아냄 → 수동 diff로 원인 규명
- 조치: `merge_undersized()`로 재작성, 양수 인덱스 + 새 리스트 반환
- **재발 방지**: 빌더에 보존 불변식 `assert`를 심었다(T-10). 입력 조각 ID 집합과 출력
  버킷의 조각 ID 집합이 정확히 일치하지 않으면 빌드가 실패한다.

이 버그는 조용했다. 출력 청크 수는 정상으로 보였고, 중복 시험이 없었다면 넘어갔을 것이다.

### B-2 — 꼬리 버킷만 병합해 중간에 소형 버킷 잔존

사내 정보(포털 주소, 온콜 경로, 예산 실측치, 법무 판단)는 **채우지 않았다.**
추측해서 적으면 그럴듯한 오답이 되고 RAG 사용자가 그대로 따른다.
필요한 항목을 [`INTERNAL-FILL-INS.md`](INTERNAL-FILL-INS.md)에 담당·우선순위와 함께 정리했다.

### 3단계 — `auto-merged` 46건 질문 개선
템플릿 전용 생성("X 운영 시 주의점은?")을 **본문 소제목 기반**으로 교체했다.
실측 신호: H3/H4 소제목 45/46 청크, 굵은 용어 46/46 청크 보유.

| | 개선 전 | 개선 후 |
|---|---|---|
| 청크당 질문 | 3.57 | **4.08** |
| v2.3 유래 질문 수 | 168 | **218** |
| 한글 조사 오류 | (미측정) | **0** |

조사 오류는 종성 판별(`josa()`)로 제거했다 — "워크플로우은" 같은 질문은 실제 질의와
겹치지 않는다.

### 4단계 — BM25 검색 평가 (T-12의 실행 가능한 절반)

dense 검색은 벡터 DB가 없어 못 돌리지만 BM25는 순수 파이썬으로 가능하다.
이 코퍼스는 영어 식별자 비중이 높아 어휘 검색이 하이브리드의 실제 한 축이다.

| 색인 대상 | Recall@1 | Recall@10 | MRR | 실패율 |
|---|---|---|---|---|
| 제목+태그+질문+본문 | 0.983 | 1.000 | 0.991 | 0.0% |
| 제목+태그+질문 | 0.983 | 1.000 | 0.991 | 0.0% |
| **본문만** | **0.505** | **0.944** | **0.668** | **5.6%** |

**앞의 두 줄은 아무것도 측정하지 않는다.** `retrieval_questions`로 골든셋을 만들고
그 질문을 색인에 넣었으므로 정답을 색인해 두고 그걸로 찾은 것이다.
Recall@10 = 1.000은 성능이 아니라 **누출**이다. 시험 계획이 경고한 낙관 편향이
예상보다 훨씬 컸다(사실상 측정 불가 수준).

**본문 전용 모드가 유일하게 유효한 수치**다. Recall@10 0.944는 하이브리드의 하한이다.

#### 발견 — 다주제 어트랙터
본문 전용 색인에서 오답 1위를 집계한 결과:

| 청크 | 오답 1위 횟수 | 토큰 |
|---|---|---|
| `v3-faq` | **53** | 1,052 |
| `v3-08-context-engineering-01` | 11 | 1,202 |
| `v3-05-claude-md-memory-02` | 10 | 992 |

`v3-faq`는 크기가 정상 범위인데도 어트랙터로 작동한다. 원인은 **다주제**다 —
FAQ는 여러 주제를 얕게 다뤄 많은 질의에 부분 매칭되고, 그 주제를 깊이 다루는 청크의
top-1을 뺏는다.

#### 실패 23건의 성격 — 실제 오답률은 더 낮다
실패 사례를 열어보니 상당수가 **오답이 아니다.**

| 질의 | 라벨 정답 | 검색 1위 |
|---|---|---|
| Claude Code에 MCP 서버를 어떻게 등록하는가? | `v3-cli-registration` | `v3-03-mcp-setup` (이것도 옳음) |
| MCP와 Skills 중 무엇을 먼저 만들어야 하는가? | `v3-component-selection` | `v3-faq` (해당 Q가 실제로 있음) |

**골든셋의 단일 정답 라벨 편향**이다. 5.6%의 실패율은 실제 오답률을 과대평가한다.
다음 반복에서 골든셋을 복수 정답 허용으로 바꿔야 한다.

## 10. 스키마 슬롯·T-13·업로드 어댑터 (2026-08-05 추가)

0이고, 나중에 필드를 추가하면 100청크 재빌드·재임베딩이 필요하다.**

### 스키마 슬롯
`source_anchor`(원문 좌표)와 `assets`(이미지)를 정본 스키마에 추가했다(`kb/schema.md`).

항상 실린다(다운스트림 코드가 `KeyError`를 안 만나게).

설계 원칙: **검색은 텍스트로, 제시는 원문으로.** 검색은 청크의 caption/description
텍스트로 하고, 답변 시점에 `source_anchor`로 원본 페이지·이미지를 불러온다.

### T-13 — 그리고 그 자기시험
검사 항목: 깨진 에셋 경로, `caption`/`description_by` 누락, `screened != true`,

선언된 에셋이 0건이라 T-13은 그냥 PASS한다. **한 번도 발화한 적 없는 검사는 작동을

만들고 감사가 FAIL을 내는지 게이트에서 확인한다.

```
$ python3 tools/kb_audit.py tests/fixtures/t13_broken/chunks --repo-root .
```

빌더에도 게이트를 넣었다 — `screened != true`인 에셋이 있으면 **빌드 자체가 중단**된다.

### 업로드 어댑터
v2.3 스크립트 6종은 형식이 달라(JSON 배열 vs JSONL, 평면 vs 중첩) 그대로는 못 쓴다.
더 중요한 건 **벡터 DB마다 메타데이터 타입 제약이 다르다**는 점이다.

| 타깃 | 리스트 | 중첩 객체 | 어댑터 처리 |
|---|---|---|---|
| ChromaDB | ✗ | ✗ | 리스트 → 쉼표 결합 |
| Pinecone | ✅ | ✗ | 중첩 → JSON 문자열 |

| Qdrant / FAISS / JSONL | ✅ | ✅ | 그대로 |

평탄화가 no-op이 아님을 확인했다:


`--dry-run`은 외부 패키지 없이 돌아 CI에서 6개 타깃 전부 검증한다.
**실제 임베딩 생성과 DB 적재는 클라이언트 패키지가 없어 실행하지 못했다.**

## 12. 검색 검증 하네스 실측 (2026-08-08)

### 12.1 복수 정답 qrels — 단일 라벨 편향의 크기

§9가 "5.6% 실패율은 실제 오답률을 과대평가한다"고 적었다. 그 크기를 실제로 쟀다.

자동으로 얻어지는 복수 정답은 **완전히 같은 질의 2건뿐**이다. 나머지는 사람 판정이
필요하며, 후보 청크를 직접 읽어 18건을 `tests/qrels_adjudicated.jsonl`에 기록했다.

| 자동 세트 (본문 전용, 청크 101개) | 판정 전 | 판정 후 |
|---|---|---|
| Recall@1 | 0.5097 | **0.5300** |
| Recall@10 | 0.9440 | **0.9574** |
| Success@10 | 0.9440 | **0.9708** |
| MRR@10 | 0.6730 | **0.7071** |
| nDCG@10 | 0.7398 | **0.7590** |
| 검색 실패율 | 0.0560 | **0.0292** |

실패율이 5.6% → **2.9%**로 내려가 시험 계획의 목표(≤3%)를 충족한다.
**검색기는 하나도 바뀌지 않았다** — 라벨을 고친 것뿐이다.

> 판정 18건은 `by: claude-opus-5`, `review_status: unreviewed`다. 사람 판정이 아니다.
> 근거가 부족한 사례는 등급을 주지 않았다 — 예를 들어 "3단계 로드맵은?"은
> `v3-roadmap`만 정답으로 남겼다. `v3-gradual-autonomy`는 자율성 단계이지 3단계
> 로드맵이 아니기 때문이다.

### 12.2 held-out 세트 — 자동 골든셋이 재지 못한 것

`docs/TEST-PLAN.md` §3이 필수 보완으로 지정했던 항목이다. 본문 어휘를 의도적으로
피한 구어체 질의 40건을 작성했다(`origin: llm-authored` — **실제 사용자 로그가 아니다**).

| 본문 전용 색인 | 자동 세트 | held-out |
|---|---|---|
| Recall@10 | 0.9574 | **0.2667** |
| nDCG@10 | 0.7590 | **0.1796** |
| MRR@10 | 0.7071 | **0.1993** |

**격차가 시험 계획의 예상보다 훨씬 크다.** 실패 사례를 열어보니 라벨이 틀린 것이
아니라 검색이 못 찾은 것이었다 — "여러 작업을 한꺼번에 돌리려는데 소스가 서로
꼬입니다"의 답은 `v3-git-worktree`인데 1위는 `v3-mcp-gateway`였고,
"설치가 제대로 됐는지 한 번에 점검하는 명령"의 답 `v3-doctor-command`는 상위 10에도
들지 못했다. 어휘 불일치다.

이 방향은 자동 세트에도 이미 나타나 있었다. 출처별 분해에서 **사람이 쓴 `authored`
질문이 늘 가장 낮았다**(Recall@10 0.886 vs 기계 생성 `v2.3` 0.972).
질문이 사람 어휘에 가까울수록 점수가 떨어진다. held-out은 그 곡선의 연장선이다.

**따라서 지금까지 보고돼 온 0.944는 실제 질의에서의 성능이 아니다.**

### 12.3 뷰 조합 — 무엇이 실제로 도움이 되는가

held-out 질의는 `retrieval_questions`에 없으므로 `fields` 뷰가 누출이 아니다.
프로덕션 설정을 처음으로 정직하게 잴 수 있었다.

| 구성 | nDCG@10 | Recall@10 | Success@10 |
|---|---|---|---|
| `body` 단독 | 0.1796 | 0.2667 | 0.500 |
| `fields` 단독 (제목+태그+질문) | 0.3176 | 0.3833 | 0.550 |
| `index` 단독 (제목+카테고리+태그+use_cases) | 0.3364 | 0.3625 | 0.525 |
| `body`+`fields` RRF | 0.2895 | 0.4083 | 0.600 |
| `body`+`fields`+`index` RRF | 0.3681 | 0.4750 | 0.675 |
| 위 + 그래프 1홉 | **0.3730** | **0.4750** | 0.675 |
| 위 + MMR 재순위 | 0.3653 | 0.4750 | 0.675 |

읽을 점 네 가지.

1. **한 줄짜리 메타데이터(`index`)가 본문 전체보다 낫다.** 구어체 질문은 산문보다
   주제 라벨에 걸린다. 에이전트용 라우팅 색인으로 만든 것이 검색 개선이기도 했다.
2. **`fields`를 색인하는 프로덕션 설정은 옳았다.** doc2query 성격의 확장이 nDCG를
   거의 두 배로 올린다. 잘못된 것은 색인이 아니라 그 질문으로 평가한 것이었다.
3. **융합은 공짜가 아니다.** `body`+`fields`는 Success@10을 0.50 → 0.60으로 올리지만
   nDCG는 `fields` 단독보다 낮다. 약한 순위가 상위를 희석한다. 세 번째 뷰를 넣어야
   이 손해가 뒤집힌다.
4. **MMR과 4-gram 뷰는 도움이 되지 않았다.** MMR은 nDCG를 0.3681 → 0.3653으로
   떨어뜨렸고 4-gram 뷰는 모든 지표를 낮췄다. 둘 다 채택하지 않았다.

`kb/ingestion.yaml`의 `retrieval` 절은 이 표를 근거로 다시 썼다. 예전에는 hybrid·
rerank·2홉 확장을 **선언만** 하고 구현도 수치도 없었다. 이제 각 항목이 `measured`
플래그와 근거를 함께 갖는다.

**절대값이 낮다는 점을 흐리지 않는다.** 어휘 검색만으로는 held-out Recall@10 0.475가
상한이다. 나머지는 dense에 있고, 그것은 아직 측정하지 못했다.

### 12.4 어트랙터 (T-15)

§9가 발견한 `v3-faq`의 top-1 탈취가 지표로 승격됐다.

| 세트 / 구성 | `v3-faq` 탈취 |
|---|---|
| 자동 세트, `body` 단독 | 49회 (자기 질문 10개) |
| held-out, `body` 단독 | 25 / 40회 |
| held-out, 3뷰 융합 + 1홉 | **2회** |

FAQ는 질문 형태의 문장으로 가득해 **질문 형태의 어떤 질의에도 부분 매칭된다.**
`index` 뷰는 주제 라벨로 매칭하므로 이 효과를 거의 없앤다. 청크 분할 없이 완화된 셈이지만,
자동 세트의 49회는 그대로다 — 분할은 여전히 조치 목록에 남는다(§13).

### 12.5 음성 질의 — 점수 하한은 작동하지 않는다

KB 범위 밖 질의 20건을 만들었다. 일부는 KB 용어와 일부러 겹치게 했다
(React의 hook, 법인카드 한도, 앱 스토어 심사).

| 지표 | 값 |
|---|---|
| 분리도 AUC | **0.5913** (0.5 = 신호 없음) |
| 1위 점수 중앙값 — 범위 안 | 14.80 |
| 1위 점수 중앙값 — 범위 밖 | 13.70 |

두 분포가 거의 겹친다. 어떤 하한을 잡아도 범위 밖을 막는 만큼 범위 안을 버린다
(하한 14에서 범위 밖 30%를 통과시키면서 범위 안 42%를 기권한다).

**그래서 `ingestion.yaml`에 `score_floor`를 적지 않았다.** 작동하지 않는 통제를
설정 파일에 적어두면 그것이 작동한다고 믿게 된다. `score_floor: null`과 AUC를 함께
기록했다. 기권 판정에는 재순위 모델이나 상대 신호가 필요하다.

### 12.6 T-11 부분 실행 — MCP 2026-07-28 전수 대조

U-001의 차단 사유는 "modelcontextprotocol.io가 HTTP 403"이었다. 렌더링된 사이트는
여전히 막혀 있으나 **사양 저장소의 원문 마크다운은 raw.githubusercontent.com으로
