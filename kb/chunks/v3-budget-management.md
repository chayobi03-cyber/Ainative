# 비용 예산 책정과 한도 관리

## 한 줄 요약
절감 기법(캐싱·라우팅)은 **평균**을 낮추고, 예산 관리는 **꼬리 위험**을 막는다.
둘은 다른 문제이며, 사고는 언제나 꼬리에서 난다.

> **집필 근거**: 원본 리서치는 prompt caching·ccusage·모델 라우팅 등 절감 레버를 다뤘지만
> "얼마를 배정하고 어디서 끊을 것인가"는 없었다. 아래 임계값은 원본에 기록된 사고 사례
> (3일 $47,000, Microsoft 롤아웃 철회, 서브에이전트 팬아웃·autocompact 루프)에서
> 역산한 **출발점 제안**이며 사내 실측 2주 후 반드시 재조정해야 한다.

## 왜 한도가 먼저인가
원본에 기록된 비용 사고의 공통 구조는 동일하다.
- 한 팀이 3일 만에 $47,000 기록
- Microsoft는 비용이 예산을 초과해 롤아웃을 공개 철회
- 급증 원인 1위는 **서브에이전트 팬아웃**(태스크 1개가 20개 이상 병렬 스폰), 2위는 **autocompact 루프**

공통점: 사람이 알아차렸을 때는 이미 발생한 뒤였다. **사후 리포트가 아니라 사전 한도**가 필요하다.

## 3계층 한도 설계

| 계층 | 대상 | 조치 |
|---|---|---|
| **하드 한도** | 조직 전체 월 예산 | 초과 시 신규 세션 차단 |
| **소프트 한도** | 팀/프로젝트 주간 예산 | 80% 도달 시 알림, 100%에서 승인 필요 |
| **런타임 상한** | 단일 세션·태스크 | 서브에이전트 병렬 수 상한, 최대 반복 횟수 |

**런타임 상한이 가장 중요하다.** 월 예산은 사고를 사후에 알려줄 뿐이고,
팬아웃 상한만이 $47,000 유형의 사고를 실시간으로 막는다.

## 예산 수립 절차
1. **측정 먼저 (2주)** — `ccusage`로 실사용을 수집한다. 추정으로 예산을 잡지 않는다.
   ```bash
   ccusage daily --breakdown     # 모델별 분해
   ccusage blocks --live         # 실시간 5시간 과금 윈도우
   ```
2. **1인당 기준선 산출** — 중앙값이 아니라 **p90**을 쓴다. 평균 사용자는 예산을 안 태운다.
3. **버퍼 배정** — 기준선 × 인원 × 1.3. 나머지 30%는 파일럿·실험 몫으로 분리 계정에 둔다.
4. **재조정 주기** — 월 1회. 모델 가격은 도입기 할인이 걸려 있어 변동한다.

## 알림 임계 (출발점)
| 신호 | 임계 | 조치 |
|---|---|---|
| 일간 사용량 | 기준선의 3배 | 즉시 알림, 해당 세션 확인 |
| 단일 세션 비용 | 일간 팀 예산의 10% | 세션 중단 후 리뷰 |
| 캐시 히트율 | 60% 미만 | 프롬프트 프리픽스 구조 점검 |
| 서브에이전트 동시 수 | 상한의 80% | 팬아웃 경고 |

## 비용 사고 대응 순서
1. 해당 세션·에이전트를 먼저 정지한다(원인 분석은 나중).
2. `ccusage daily --breakdown`으로 모델·시간대를 특정한다.
3. 팬아웃인지 루프인지 구분한다 — 팬아웃은 짧은 시간 다수 호출, 루프는 동일 패턴 반복.
4. 런타임 상한을 조이고 재개한다.
5. 사후: 회귀 게이트에 "토큰 사용량 회귀" 항목을 추가한다.

## 놓치기 쉬운 항목
- **모델 업그레이드 시 토크나이저가 바뀌면 같은 텍스트의 토큰 수가 늘어난다.** 원본은 Claude 4.7
  이후 모델에서 약 30% 증가를 보고한다. 모델을 올릴 때 예산도 함께 재계산한다.
- **캐싱은 입력 토큰만 할인한다.** 출력은 절대 할인되지 않으므로 출력이 긴 워크로드는
  캐싱으로 해결되지 않는다.
- 모델 가격 배수를 코드에 하드코딩하지 않는다. 설정으로 뺀다.
