# 멀티 에이전트 오케스트레이션 — 패턴 선택과 실패 모드

## 한 줄 요약
2026년 프로덕션 기본값은 **supervisor(계층적 위임)**다. 구조 선택보다 **핸드오프 설계**가
성패를 가르며, 최대 실패 모드는 무한 핸드오프 루프와 단계마다 누적되는 컨텍스트 손실이다.

> **출처 등급 주의.** 이 청크의 수치(도입 실패율, 비용 절감폭)는 **2차 출처 취합**이다
> (`kb/corrections.yaml` U-004). 패턴 분류와 실패 모드는 여러 보고에서 일관되게
> 관찰되지만, **숫자를 사내 목표치로 그대로 쓰지 말 것.** 사내 실측이 선행돼야 한다.

## 먼저 물을 것 — 정말 여러 에이전트가 필요한가

에이전트를 늘리면 조율 비용과 실패 지점이 함께 늘어난다. 다음이 아니면 단일 에이전트가 낫다.

- 하위 작업이 **서로 다른 도구 권한**을 요구한다 (권한 분리가 목적)
- 하위 작업이 **독립적이고 병렬화 이득이 크다**
- 하위 작업이 **컨텍스트를 오염시킨다** (긴 로그 분석 등 — 격리가 목적)
- 서로 다른 **관점의 검토**가 필요하다

"복잡하니까 나눈다"는 이유가 되지 않는다. 나누면 복잡도는 옮겨갈 뿐 줄지 않는다.

## 패턴 5종과 선택 기준

| 패턴 | 구조 | 언제 |
|---|---|---|
| **supervisor** | 상위가 분해·위임·취합 | **기본값.** 책임 소재가 분명하고 비용 통제가 쉽다 |
| **fan-out** | 병렬 산개 후 취합 | 하위 작업이 독립적이고 순서가 없을 때 |
| **pipeline** | 순차 연결 | 각 단계가 앞 단계 결과를 꼭 필요로 할 때 |
| **debate** | 여러 관점이 비판 | 판단이 갈리는 문제. 비용이 배수로 든다 |
| **swarm** | 동적 peer 간 위임 | 마지막에 고려할 것. 아래 실패 모드가 여기서 가장 심하다 |

**supervisor부터 시작한다.** 위임 경로가 한 방향이라 루프가 구조적으로 생기지 않고,
어느 단계에서 실패했는지 추적할 수 있다.

## 실패 모드 — 설계 시점에 막아야 하는 것

### 1. 무한 핸드오프 루프 (최다 보고)

A가 B에게, B가 C에게, C가 다시 A에게 넘긴다. 각자는 "내 일이 아니다"라고 판단했을 뿐인데
전체는 멈추지 않는다.

**막는 법 — 구조로 막는다. 프롬프트로 막지 않는다.**
- 핸드오프 **깊이 상한**과 **총 횟수 상한**을 하네스가 강제한다
- 위임 그래프를 **비순환으로 제한**한다 (supervisor가 이걸 공짜로 준다)
- 상한 도달 시 실패가 아니라 **사람에게 에스컬레이션**한다

### 2. 컨텍스트 손실 누적

단계마다 컨텍스트를 넘겨야 하는데 선택지가 둘 다 나쁘다 —
전체를 넘기면 비용이 커지고 결국 창을 넘기며, 요약하면 손실이 쌓인다.

**실무 해법**: 컨텍스트를 넘기지 말고 **참조를 넘긴다.** 원본을 파일이나 저장소에 두고
경로·식별자만 전달하면, 필요한 에이전트가 필요한 만큼만 읽는다.
이 KB의 `kb/INDEX.md` → 청크 구조가 같은 원리다.

### 3. 조율이 작업보다 비싸짐

토큰의 대부분이 "누가 무엇을 할지 정하는 데" 쓰인다. 하위 작업 하나당 왕복이 여러 번이면
단일 에이전트보다 느리고 비싸다.

**점검**: 총 토큰 중 실제 산출물 생성에 쓰인 비율. 절반 아래면 구조를 의심한다.

## 비용 — 모델 티어링

상위(분해·판단)는 능력이 높은 모델, 하위(정해진 변환·추출)는 싼 모델을 쓴다.
서브에이전트에 `model:`을 명시하는 것이 이 KB가 이미 권장하는 방식이다
(`v3-model-routing` 참조).

> 2차 출처들은 40~60% 절감을 보고한다. **사내 실측 전에는 인용하지 말 것.**
> 절감폭은 상위/하위 작업 비율에 전적으로 의존하며, 조율 왕복이 많으면 오히려 늘어난다.

## 관측 — 세 층위를 나눠서 본다

| 층위 | 무엇을 | 왜 |
|---|---|---|
| agent | 개별 호출의 지연·토큰·오류 | 어느 에이전트가 문제인가 |
| **orchestration** | **라우팅 정확도, 핸드오프 성공률, 위임 깊이** | **조율 실패는 여기서만 보인다** |
| workflow | 종단 성공률, 총 비용, 총 소요 | 사용자가 겪는 것 |

**가운데 층이 가장 진단적이다.** agent 층만 보면 개별 호출은 전부 성공인데
전체는 실패하는 상황을 설명하지 못한다 — 무한 루프가 정확히 그 모양이다.

OpenTelemetry GenAI semantic conventions로 남기면 기존 대시보드와 붙는다
(`v3-observability-otel` 참조). MCP 2026-07-28은 `_meta`의 `traceparent`·`tracestate`로
트레이스 컨텍스트를 전파하는 관례를 문서화했다(`v3-mcp-2026-07-28-changes` 참조).

## 도입 순서

1. **단일 에이전트로 먼저 끝까지 만든다.** 병목이 측정되기 전에는 나누지 않는다
2. 병목이 권한 분리·병렬화·컨텍스트 오염 중 하나면 **supervisor로 나눈다**
3. 핸드오프 상한과 orchestration 층 관측을 **처음부터** 넣는다. 나중에 넣으면 이미 늦다
4. 하위 작업이 정형화되면 모델을 낮춘다
5. debate·swarm은 위 넷이 부족하다는 **측정 결과가 나온 뒤에** 고려한다

## 사내 실측이 필요한 항목

- 조율 토큰 비율 (총 토큰 대비 산출물 생성 토큰)
- 핸드오프 평균 깊이와 상한 도달 빈도
- 모델 티어링 전후 실제 비용 변화
- 단일 에이전트 대비 종단 성공률

이 넷을 재기 전에는 어떤 구조가 나은지 알 수 없다. 2차 출처의 수치는 출발점이지 목표가 아니다.
