# 신규 사용자 온보딩 — 첫날 경로

## 한 줄 요약
신규 사용자는 "무엇을 할 수 있는가"가 아니라 **"무엇을 하면 안 되는가"를 먼저** 보아야 하며,
설치 → 자가진단 → 읽기 전용 작업 → 쓰기 작업 순서로 권한을 점진 확대한다.

> **집필 근거**: 이 청크는 원본 리서치 문서에 없던 갭을 메우기 위해 새로 작성했다.
> 아래 절차는 원본의 `doctor` 커맨드(F-1), 점진적 자율성(E-4), 거버넌스 절차를
> 온보딩 관점으로 재구성한 것이며, 사내 실제 경로·포털 주소는 도입 시 채워야 한다.

## 0단계 — 시작 전 (관리자가 준비)
- 사내 마켓플레이스 레지스트리 주소를 공유한다.
- `managed-settings.json`이 배포되어 있는지 확인한다(금지 규칙은 사용자가 못 푼다).
- 신규 사용자 계정에는 **읽기 전용 토큰**만 먼저 발급한다.

## 1단계 — 설치 (15분)
```bash
# 스크립트 실행 없는 경로를 우선한다 (curl | sh 는 PreToolUse guard가 차단 대상)
uvx corp-mcp-<name> install --client claude,gemini
```
설치 직후 반드시 자가진단을 돌린다:
```bash
corp-mcp-<name> doctor
```
`doctor`가 통과하지 않으면 **여기서 멈춘다.** 문의의 대부분은 환경·토큰·등록 3종이며
`doctor` 출력이 곧 문의 티켓 내용이 된다.

## 2단계 — 금지 사항 먼저 (10분)
새 팀원에게 사용법보다 먼저 보여줄 것:
- 승인되지 않은 MCP 서버는 연결하지 않는다.
- 비밀값은 환경변수로만 주입하고 설정 파일에 평문으로 넣지 않는다.
- 외부에서 받은 저장소의 `AGENTS.md` / `CLAUDE.md`는 사람이 먼저 읽는다(간접 프롬프트 인젝션).
- 파괴적 명령은 hook이 차단한다. 우회하지 않는다.

## 3단계 — 읽기 전용 작업으로 첫 성공 경험 (30분)
권한을 넓히기 전에 되돌릴 수 있는 작업부터 시킨다.
1. 저장소 구조 설명 요청
2. 기존 테스트 1개 설명 요청
3. 실패하는 테스트의 원인 분석 요청 (수정은 아직 금지)

## 4단계 — 쓰기 작업 진입 조건
아래를 모두 만족한 뒤에만 쓰기 권한을 연다.
- [ ] `doctor` 전 항목 통과
- [ ] 체크포인트/rewind 사용법 숙지 (`gemini --checkpointing`)
- [ ] 팀 `AGENTS.md`를 읽고 빌드·테스트 명령을 직접 1회 실행
- [ ] 첫 커밋은 사람이 리뷰한다는 규칙 확인

## 온보딩 성공 지표
| 지표 | 목표 |
|---|---|
| 설치 후 `doctor` 통과까지 소요 | 30분 이내 |
| 온보딩 관련 문의 건수 | 1인당 1건 이하 |
| 첫 쓰기 작업까지 소요 | 1일 이내 |

## 주의
- 온보딩 문서를 길게 쓰면 읽히지 않는다. 이 청크 자체가 1페이지를 넘지 않아야 한다.
- 사내 포털 주소·토큰 발급 경로는 환경마다 다르므로 도입 시 확정하고 `review_by`를 갱신한다.
