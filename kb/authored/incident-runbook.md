# 장애 대응 런북 — 에이전트/MCP 운영 사고

## 한 줄 요약
에이전트 장애는 **크래시가 아니라 "형식은 맞지만 틀린 결과"로 나타난다.**
따라서 1차 판단은 "돌고 있는가"가 아니라 **"맞는 답을 내고 있는가"**여야 한다.

> **집필 근거**: 원본 리서치는 재시도·timeout·circuit breaker·fallback 모델 같은 개별
> 기법을 나열했지만 사고 시 실행 순서는 없었다. 아래는 그 기법들을 대응 순서로 엮은
> 설계안이며, 사내 온콜 체계에 맞춰 연락 경로와 권한자를 채워야 한다.

## 심각도 분류

| 등급 | 정의 | 목표 대응 |
|---|---|---|
| **S1** | 잘못된 결과가 외부/고객에게 나감, 데이터 손상, 비용 폭주 | 즉시 정지 |
| **S2** | 사내 사용자가 잘못된 결과를 받음, 골든셋 pass rate 급락 | 1시간 내 |
| **S3** | 일부 툴 실패, 응답 지연 | 당일 |
| **S4** | 품질 저하 의심, 재현 불가 | 다음 스프린트 |

## 1차 대응 (순서 고정)

### 1) 멈춘다
원인 분석보다 확산 차단이 먼저다.
- 비용 폭주 → 해당 세션·에이전트 정지
- 잘못된 쓰기 → 해당 MCP 서버 비활성화 (`.mcp.json`에서 제거 또는 managed deny)
- 전면 장애 → feature flag로 에이전트 경로 자체를 끈다

### 2) 범위를 확정한다
- 언제부터인가 — 트레이스에서 첫 이상 시각
- 무엇이 바뀌었나 — 모델 버전 / 프롬프트 / 툴 정의 / 사양 / 의존성 중 하나다
- 얼마나 나갔나 — 영향받은 세션·사용자·산출물 수

### 3) 되돌린다
가장 최근 변경부터 역순으로 되돌린다. **한 번에 하나씩** 되돌려야 원인이 특정된다.

| 변경 유형 | 롤백 수단 |
|---|---|
| 모델 버전 | 이전 버전으로 pin |
| 프롬프트/정책 | remote config로 즉시 전환 |
| 툴 정의 | 이전 서명/해시 버전으로 복귀 |
| 플러그인 | 마켓플레이스에서 이전 버전 재설치 |

## 원인별 진단 분기

**툴 호출은 되는데 결과가 틀림** → 툴 description 또는 스키마 드리프트.
`mcp-eval` 골든셋을 돌려 어느 케이스가 깨졌는지 특정한다.

**툴을 아예 안 부름** → description 트리거 실패 또는 툴 정의가 컨텍스트에서 밀림.
서버 수가 늘어 툴 정의 토큰이 커졌는지 확인한다.

**연결 실패** → stdout 오염(JSON-RPC 파서 붕괴)을 최우선 의심한다. 로그가 stderr로 가는지 확인.

**간헐적 실패** → 비결정성이다. 같은 입력 3회 실행해 뒤집히는지 본다.
10% 이상 뒤집히면 판정 기준 자체가 문제다.

**비용 급증** → 서브에이전트 팬아웃 또는 autocompact 루프.

## 재개 조건
- [ ] 원인이 특정되었다(추정 아님)
- [ ] 골든셋 재실행 pass rate ≥ 90%
- [ ] 동일 사고를 잡는 테스트 케이스가 회귀셋에 추가되었다
- [ ] 카나리 5%로 먼저 재개하고 online eval이 control과 유의차 없음을 확인

## 사후 분석에 반드시 남길 것
- 탐지까지 걸린 시간 — 이게 길면 관측이 부족한 것이다
- 사람이 먼저 알아차렸는가, 알림이 먼저였는가
- 회귀 게이트가 왜 못 막았는가
- 추가된 테스트 케이스 ID

## 안티패턴
- **성공으로 위장하지 않는다.** 에이전트가 실패를 그럴듯한 답으로 덮으면 탐지가 늦어진다.
  사용자에게 정직하게 실패를 알리는 편이 언제나 낫다.
- 원인 모른 채 재시도만 반복하지 않는다. 비멱등 작업에서는 재시도가 피해를 키운다.
- 사고 중 여러 개를 동시에 되돌리지 않는다. 원인을 영원히 못 찾는다.
